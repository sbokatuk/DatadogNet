## DatadogNet 3.14.0.2

A correctness fix on iOS, the tests that should have caught it, and the 3.x view-scoped API that
was held back from the previous release.

Native versions are unchanged — dd-sdk-ios **3.14.0** and dd-sdk-android **3.12.1**. Existing code
compiles untouched; the only signature changes are additions.

### Added: view-scoped attributes

The best thing the 3.x SDKs added, and the reason `IRumViewScope` grew rather than `IRumMonitor`.
Attributes set on a view propagate to the actions, resources, errors and long tasks reported inside
it, and go away with the view — so the three keys you were repeating on every call can be set once:

```csharp
using var view = Datadog.Rum.StartView ("checkout");
view.AddAttributes (new Dictionary<string, object?> { ["cart.id"] = cartId });

// Everything below carries cart.id, with nothing passing it along.
Datadog.Rum.AddAction (RumActionType.Tap, "apply-coupon");
Datadog.Rum.AddError (exception);
```

Also on `IRumViewScope`:

- **`RemoveAttributes(keys)`** — unknown names are ignored, as both SDKs do.
- **`AddLoadingTime(overwrite: false)`** — how long the view took to become *useful*, which is rarely
  when it appeared. Both SDKs keep the first value unless `overwrite` says otherwise.

And on `IRumMonitor`:

- **`ReportAppFullyDisplayed()`** — time-to-interactive. Both SDKs measure time-to-first-frame
  themselves, but a MAUI app is usually not finished at its first frame.

Calls after the scope has stopped are dropped rather than forwarded. Neither SDK takes a view key
for these — they apply to whatever view is currently active — so forwarding a late call would
silently write onto whatever view came next.

These are available on both platforms; the four native members line up exactly.

### Fixed: `IDatadogSpan.TraceId` was wrong on iOS

The same span reported two different things depending on the platform:

```
iOS      trace 6096355397431041644                  ← decimal, low 64 bits only
Android  trace 6a61e4ff000000002e430f579ece9a6c     ← hex, all 128 bits
```

Not just a different format — a different width, and the iOS one was lossy. It matters beyond
cosmetics: `DatadogHttpMessageHandler` writes `_dd.trace_id` onto every RUM resource, and that
attribute is the only thing linking a RUM resource to its APM trace.

**If you correlated RUM resources to traces on iOS, that link was broken.** Android was unaffected.

There is a right answer, and it comes from dd-sdk-android's own `DatadogInterceptor` — the reference
implementation of this exact correlation:

| Attribute | Rendering |
| --- | --- |
| `_dd.trace_id` | `DatadogTraceId.toHexString()` — 32 lowercase hex characters, always |
| `_dd.span_id` | `String.valueOf(long)` — decimal |

The asymmetry is the wire format, not an oversight. And `toHexString()` is
`toHexStringPadded(…, 32)` on both the 128-bit and 64-bit implementations, so a 64-bit id renders as
the low half behind sixteen zeros — never as a 16-character string.

Android already did exactly this. iOS now does too, which takes some work, because `OTSpanContext`
exposes no ids at all: the id is reassembled from the two places the Datadog headers split it
across — the decimal low half in `x-datadog-trace-id`, and the high half as `_dd.p.tid` inside
`x-datadog-tags`.

`SpanId` was already correct on both platforms and is unchanged.

### Added: `DatadogNet.UnitTests`

66 tests against the neutral assembly — no device, no emulator, no packages, about 15 milliseconds.
This is the layer that was missing entirely, and it is where the bug above would have been caught:

- **`TraceIdentifiers`** — reassembly, the 64-bit padding case, malformed and adversarial `_dd.p.tid`
  values, boundary ids, case handling.
- **`DatadogHttpMessageHandler.IsFirstParty`** — the suffix-on-a-label-boundary matching that decides
  whether a host is handed your trace ids. `notexample.com` must not match `example.com`; an empty
  entry in the host list must not match everything. This is the one place in the façade where a quiet
  mistake is a leak rather than a missing dashboard, and it had no coverage at all.
- **`ActiveSpanTracker`** — nesting and restore, double dispose, and the deliberate
  `[ThreadStatic]`-not-`AsyncLocal` decision, now asserted rather than only documented.
- **`Datadog.Initialize`** validation — every rejection path, and that a sample rate of `0` is
  accepted rather than mistaken for unset.

The matching logic in `DatadogHttpMessageHandler` was split into a pure overload to make this
possible; the public API is unchanged.

### Tightened: the device checks

The trace check asserted `TraceId.Length > 0`, which is why twenty green runs never noticed. It now
asserts:

- the trace id is 32 lowercase hex characters and not all zeros
- the span id is decimal
- the id's low half matches the `x-datadog-trace-id` header the SDK itself emitted
- the id agrees with `traceparent` across all 128 bits — an independent second opinion from the
  SDK's own W3C writer, which is derived separately from everything above

Verified on both platforms: iOS now reports `6a61ec6d00000000a25ebf9b34ae45d4`.
